## 1. N-01：材料パーサのテストケース表

**テストケース表はドキュメントではなくコードに置く。**

- 仕様：[`src/ingredients/parser.ts`](../src/ingredients/parser.ts)
- テストケース表：[`src/ingredients/parser.test.ts`](../src/ingredients/parser.test.ts)

```bash
npm test
```

### なぜコードに置くのか

| # | 理由 |
|---|---|
| T-01 | 表をドキュメントに書くと、実装と乖離しても誰も気づかない。テストなら CI で乖離が落ちる |
| T-02 | **テストケースの入力はすべて実データに実在した表記**。机上の想定ではないため、パーサ改良時の回帰検出として機能する |
| T-03 | 不変条件（結果の先頭・末尾に記号が残らない／括弧が残らない）を全ケースに対して自動検証している |

## 3. 食材辞書の整備戦略（データに基づく優先順位）

パース後の食材名5,195件を出現頻度順に並べ、累積カバー率を測定した。

| 辞書に登録する件数 | 全材料エントリのカバー率 |
|---|---|
| 100件 | 56.4% |
| 300件 | 72.0% |
| **500件** | **77.8%** |
| 1,000件 | 84.5% |
| 2,000件 | 90.1% |
| 5,195件（全件） | 100% |

**出現1回だけの食材名：3,491件**（全体の67%を占めるが、カバー率への寄与は極小）

### 決定：D-10 辞書は頻度上位から整備し、ロングテールは追わない

| # | 決定 |
|---|---|
| D-10 | **辞書整備の初期目標を「頻度上位500件」とする。** これで材料エントリの77.8%をカバーできる。5,195件すべてを整備しようとしない |

**根拠**：
残りの3,491件は出現1回のみであり、1件整備してもカバー率は0.003%しか上がらない。
一方、未登録の食材は `ingredient_id = NULL` となり **D-04 により自動的にスコアの分母から外れる**ため、
辞書が不完全でも検索は破綻しない。**辞書の完成度と検索の正しさが独立している**構造になっている。

> これは第6章「正規化できなかった材料を頻度順で出力し、上位から辞書へ追加する」という
> 基本設計の方針が、実データで裏付けられたものである。

### 実績（2026-09-20 時点）

D-10 の目標「上位500件で77.8%」に対し、**より少ない登録数で目標を上回った**。
表記ゆれ（synonyms）と階層（parent）により、1エントリが多数の表記を吸収するため。

| 指標 | 実測 |
|---|---|
| 辞書の正規形エントリ数 | **218件** |
| 別名込みの表記数 | 約570件 |
| **材料エントリのカバー率** | **84.7%** |
| 食材でないと判定（パーサ段階） | 1.8% |
| 辞書未登録 | 13.5% |
| 材料を100%解決できたレシピ | 39.7% |
| **材料を50%以上解決できたレシピ** | **96.1%** |

カバー率の測定と未登録食材の頻度順出力は
[`scripts/etl/report-coverage.ts`](../scripts/etl/report-coverage.ts) で再現できる。

```bash
node scripts/etl/report-coverage.ts --list 50
```

### 意図的に辞書へ登録しないもの

未登録の頻度上位には `A` `B` `調味料` `or` `具材` `トッピング` が並ぶ。
これらは投稿者が材料欄に入れたグループ見出しや区切りであり、**食材ではない**。
パーサのバグではなく実データにそのまま存在する。
辞書に載せないことで `ingredient_id = NULL` となり、D-04 がスコアから除外する。

## 4. 実行環境メモ

| 項目 | 内容 |
|---|---|
| Node.js | v25.9.0。**TypeScript を変換なしで直接実行できる**ため、ETL とテストにビルド工程は不要 |
| テストランナー | `node:test`（標準搭載）。Jest / Vitest は導入しない |
| 型チェック | `npx tsc --noEmit`（`tsconfig.json` に `types: ["node","react"]` と `allowImportingTsExtensions` が必要） |

### ⚠️ Expo CLI は `.env` を自動で読み込む（NFR-05 に直結）

`expo` コマンド実行時、`.env` の内容が自動的に環境変数として読み込まれる。
このとき **`EXPO_PUBLIC_` で始まる変数は、アプリのバンドルに文字列として埋め込まれる**。

| # | 決定 |
|---|---|
| D-11 | **楽天の認証情報に `EXPO_PUBLIC_` 接頭辞を絶対に付けない。** 現在の `RAKUTEN_APP_ID` / `RAKUTEN_ACCESS_KEY` という命名を維持する |

**理由**：接頭辞を付けた瞬間、アプリのバイナリに認証情報が同梱され、
NFR-05「APIキー・秘密情報をアプリバイナリに含めない」に違反する。
そもそも本設計では**アプリは通信しない**（DBをバンドルする）ため、
アプリ側が認証情報を必要とする場面は存在しない。認証情報を使うのは ETL のみ。

## 5. 動作確認CLI（UI着手前の検証）

UI を作る前に検索ロジックが実用になるかを確かめるため、CLI を用意した。

```bash
node scripts/etl/build-db.ts          # 生JSON → assets/recipes.db
node scripts/search-cli.ts 玉ねぎ 豚こま 卵
```

| 項目 | 実測 |
|---|---|
| 生成DB | 4.1 MB（NFR-08 の100MB以内） |
| 収録レシピ | 4,463件 / 材料33,006件（正規化済み84.7%） |
| 検索応答 | **約75ms**（NFR-03 の500ms以内） |

### CLI で発見した設計上の欠陥（D-12 / D-13）

机上のテストでは発見できず、**実データで実際に動かして初めて分かった**もの。

| 症状 | 原因 |
|---|---|
| 「いま作れる」に卵酒・卵焼きばかり並び、玉ねぎと豚こまが使われない | `staple`が継承されず、常備品の子（日本酒）が主要材料に数えられていた（D-12） |
| 「小麦粉がある」だけでパンのレシピが作れる判定になる | `強力粉`を`小麦粉`の子にしていた。代用できないものを親子にしていた（D-13） |

修正後、「いま作れる」は115件→52件に減り、誤判定が除去された。

> **UI より先に CLI を作った判断が効いた。**
> UI を作ってから気づいていた場合、原因が検索ロジックか表示かの切り分けが必要になっていた。
