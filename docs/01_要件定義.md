# 要件定義書：音声レシピ提案アプリ

| 項目 | 内容 |
|---|---|
| 文書バージョン | 0.1（ドラフト・レビュー前） |
| 作成日 | 2026-09-20 |
| 対象 | iPhone アプリ（Expo / React Native / TypeScript） |

> 【仮】とある項目は、こちらで仮置きした前提です。レビュー時に否定・修正してください。

---

## 1. 背景・目的

冷蔵庫にある食材を起点に献立を決めたいが、既存のレシピサービスは
「作りたい料理名」から探す前提で設計されている。
また調理中・買い物直後は手が塞がっており、文字入力の負荷が高い。

本アプリは **「手を使わず、今ある食材を声で伝えるだけで、作れるレシピが出てくる」**
ことを唯一の目的とする。

### 成功の定義

> 冷蔵庫の前で 15 秒話しただけで、
> 「今日これ作ろう」と思えるレシピが 1 件以上出てくること。

レシピ件数の多さ・SNS 機能・栄養計算は成功条件に含めない。

---

## 2. 想定利用者・利用シーン

### 利用者
- 主利用者：開発者本人（自分が毎日使うことを最優先する）
- 料理スキル：レシピを見れば作れるが、献立を考えるのが面倒

### 利用シーン（最重要の設計制約）

| # | シーン | そこから導かれる制約 |
|---|---|---|
| S1 | 冷蔵庫を開けながら、片手にスマホ | **片手・1タップで録音開始できること** |
| S2 | 手が濡れている・食材で汚れている | **認識後の修正操作を最小化する。タップ前提にしない** |
| S3 | スマホをまな板の横に置き、離れて見る | **文字を大きく。1画面の情報量を絞る** |
| S4 | キッチンは電波が弱い場合がある | **オフラインで完結すること（NFR-01）** |

---

## 3. ユースケース

### UC-01 食材を声で伝えてレシピを提案してもらう（基本フロー）

1. 利用者がアプリを起動する
2. 大きなマイクボタンを 1 回タップする
3. 「玉ねぎと豚こまと卵があります」と話す
4. アプリが話し終わりを検知し、認識を確定する
5. アプリが認識した食材を**リスト表示する**（例：玉ねぎ / 豚こま切れ肉 / 卵）
6. 利用者が内容を確認し、「これで検索」をタップする
7. 作れるレシピが**カバー率の高い順**に一覧表示される
8. 利用者が 1 件選び、材料と手順を確認する

### UC-02 認識結果を訂正する（代替フロー）

- 5. の時点で誤認識があった場合、該当食材をタップして削除できる
- 不足していた食材は、マイクボタンをもう一度押して**追加で話せる**（上書きではなく追加）

### UC-03 調味料は言わなくてよい（重要な業務ルール）

- 醤油・塩・砂糖・酒・みりん・油・こしょう等は**常備品として扱う**
- 利用者がこれらを口に出さなくても、レシピ側の材料としては「所持している」と判定する
- この扱いがないと、ほぼ全レシピが「材料不足」になり提案が成立しない

## 4. 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | マイクボタンのタップで音声認識を開始し、日本語を文字列として取得する | 必須 |
| FR-02 | 認識文字列から食材名を抽出する（助詞・不要語を除去する） | 必須 |
| FR-03 | 抽出した食材名を、表記ゆれを吸収して正規形に変換する（例：たまねぎ→玉ねぎ） | 必須 |
| FR-04 | 認識・抽出した食材を一覧表示し、個別に削除できる | 必須 |
| FR-05 | 追加の音声入力で食材を追記できる | 必須 |
| FR-06 | 所持食材をもとに、ローカル DB のレシピをスコアリングして並べる | 必須 |
| FR-07 | レシピ一覧に「カバー率」と「不足している食材」を表示する | 必須 |
| FR-08 | レシピ詳細で、材料一覧・調理時間目安・費用目安を表示し、手順は元レシピページを WebView で開く（P-09 参照） | 必須 |
| FR-09 | 常備調味料リストを保持し、マッチング時に所持扱いする | 必須 |
| FR-10 | 認識できなかった／DB に無い食材を、利用者に分かる形で提示する | 推奨 |
| FR-11 | 検索結果が 0 件のとき、「あと 1 つ買えば作れるレシピ」を提示する | 推奨 |
| FR-12 | お気に入り登録（端末内保存） | 任意 |

---

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | **オフラインで全機能が動作すること。** 通信を前提としない |
| NFR-02 | マイクボタンのタップから認識開始までの体感遅延を 1 秒以内とする |
| NFR-03 | 検索（FR-06）の応答を 0.5 秒以内とする |
| NFR-04 | サーバー運用費を 0 円とする。バックエンドを持たない |
| NFR-05 | API キー・秘密情報をアプリバイナリに含めない |
| NFR-06 | 本文の文字サイズは、50cm 離れて読める大きさを下限とする |
| NFR-07 | レシピ閲覧中は画面をスリープさせない |
| NFR-08 | アプリサイズは 100MB 以内（DB バンドル込み） |
| NFR-09 | 7日ごとの再ビルドが必要（P-12）。再ビルド後もユーザーデータ（お気に入り等）を失わない設計とする |

---

## 6. スコープ外（作らないこと）

意図的に作らない。あとから欲しくなっても、まず 1 周完成させることを優先する。

- ユーザー登録・ログイン・複数端末同期
- 冷蔵庫の在庫を継続管理する機能（消費・賞味期限の管理）
- 買い物リスト生成
- 栄養価・カロリー計算
- Android 対応（【仮】まず iPhone のみ。技術的には後から可能）
- レシピの投稿・共有・SNS 連携
- 写真からの食材認識
- 読み上げ（TTS）による手順ナビ（※魅力的だが 2 周目以降）

## 7. 前提・制約

### 技術前提
| # | 内容 |
|---|---|
| P-01 | 音声認識は iOS 標準（`expo-speech-recognition` 経由の `SFSpeechRecognizer`）を使う。無料・オンデバイス |
| P-02 | 音声認識はネイティブモジュールのため **Expo Go では動作しない**。Development Build で開発する |
| P-03 | マイク動作確認は**実機を正とする**。シミュレータの結果は参考値 |
| P-04 | レシピデータは楽天レシピ API を事前巡回して構築したローカル SQLite を使う |

### データ供給元の制約（設計上の最重要事項）
| # | 内容 |
|---|---|
| P-05 | 楽天レシピ API には**食材名・キーワード検索が存在しない**。カテゴリ別ランキング取得のみ |
| P-06 | 1 カテゴリあたり取得できるのは**上位 4 件**まで。全カテゴリを巡回して件数を稼ぐ |
| P-07 | 材料は `recipeMaterial` に**自由記述**で入る（例：`"玉ねぎ 1/2個"` `"★醤油 大さじ2"`）。分量・記号を除去するパーサが必要 |
| P-08 | 取得データのローカル蓄積・再配布は楽天ウェブサービス規約の確認が必要。**個人利用に限定する**前提で進める。App Store 公開は判断を保留する |
| P-09 | API に**調理手順のフィールドが存在しない**（確認済み。取得できるのは `recipeMaterial` / `recipeIndication`（調理時間目安）/ `recipeCost`（費用目安）/ `recipeDescription`（投稿者コメント）まで）。手順は `recipeUrl` を WebView で開いて表示する |
| P-10 | 食材正規化辞書（FR-03）のシードに、文部科学省「日本食品標準成分表2020年版（八訂）」（2,478食品・別名欄つき・自由利用可）を用いる。ただし口語の表記ゆれは別途手書きで補う |
| P-11 | 日本語レシピを食材名で検索できる公開 API は存在しないことを確認済み。供給元の比較検討は ADR-001 を参照 |

### 配布に関する制約（D-02 の帰結）
| # | 内容 |
|---|---|
| P-12 | Apple Developer Program（年 $99）には加入しない。**無料 Apple ID での実機ビルドは署名が7日で失効する**ため、使い続けるには定期的な再ビルドが必要 |
| P-13 | 再ビルドの手間を減らすため、ビルド手順を `README` に記載し、コマンド一発で再署名・再インストールできる状態にする |

## 8. 決定事項（調査により確定したもの）

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| D-01 | レシピ手順の持ち方 | **DB に持たず、`recipeUrl` を外部ブラウザで開く** | 楽天レシピ API に手順フィールドが存在しないことを公式ドキュメントで確認（P-09）。副次的に、楽天サイトへ送客する形になるため規約面でも安全側 |
| D-02 | 配布範囲（Q-05） | **App Store 公開はしない。開発者本人の端末でのみ使用する** | 本アプリの成功条件は「自分が毎日使うこと」であり、公開は目的に含まれない。副次的に、Apple Developer Program（年 $99）が不要になり、楽天データ蓄積の再配布に関する規約確認（C-05）も論点から外れる |

## 9. 未決事項（レビューで決めたいこと）

| # | 論点 | 選択肢 |
|---|---|---|
| Q-02 | 「作れる」の判定基準。主要材料を 100% 満たす必要があるか、80% で許容するか | スコアリング仕様（基本設計）で確定させる |
| Q-03 | 野菜の粒度。「ねぎ」と「長ねぎ」「小ねぎ」を同一視するか | 正規化辞書の設計方針に直結する |
| Q-04 | 提案件数の上限（5 件？ 20 件？） | S3（離れて見る）を踏まえると少ない方が良い可能性 |
