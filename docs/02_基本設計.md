## 1. 設計方針

| # | 方針 | 根拠 |
|---|---|---|
| A-01 | **バックエンドを持たない。** レシピDBはビルド時にアプリへバンドルする | NFR-01（オフライン）/ NFR-04（運用費0円）/ NFR-05（APIキーを端末に置かない） |
| A-02 | **食材名の正規化ロジックを ETL とアプリで共用する** | ETLは「材料テキスト→食材名」、アプリは「音声テキスト→食材名」。同じ辞書・同じ照合規則でないと検索が一致しない。**本設計で最も重要な構造上の判断** |
| A-03 | **調理手順は持たず、外部ブラウザへ送客する** | D-01。API に手順が無く、楽天サイトへの送客は規約面でも安全 |
| A-04 | **画面遷移を浅くする** | S2（手が汚れている）/ S3（離れて見る）。タップ数と情報量を抑える |

## 4. データモデル

読み取り専用のバンドルDB（`assets/recipes.db`）。

```sql
-- レシピ本体
CREATE TABLE recipes (
  recipe_id    INTEGER PRIMARY KEY,
  title        TEXT NOT NULL,
  url          TEXT NOT NULL,   -- recipeUrl。外部ブラウザで開く
  image_url    TEXT,
  indication   TEXT,            -- recipeIndication 例:"約15分"
  cost         TEXT,            -- recipeCost 例:"300円前後"
  description  TEXT,            -- recipeDescription（投稿者コメント）
  category_id  TEXT NOT NULL
);

-- 食材マスタ（正規形）
CREATE TABLE ingredients (
  ingredient_id INTEGER PRIMARY KEY,
  name          TEXT NOT NULL UNIQUE,  -- 正規形 例:"玉ねぎ"
  kind          TEXT,                  -- 野菜/肉/魚介/乳製品/調味料 ...
  is_staple     INTEGER NOT NULL DEFAULT 0, -- 1=常備品。所持扱いする
  parent_id     INTEGER REFERENCES ingredients(ingredient_id)  -- D-03。上位食材。例:"長ねぎ".parent = "ねぎ"
);

CREATE INDEX idx_ingredients_parent ON ingredients(parent_id);

-- 表記ゆれ辞書
CREATE TABLE ingredient_synonyms (
  synonym       TEXT PRIMARY KEY,      -- "たまねぎ","タマネギ","玉葱","オニオン"
  ingredient_id INTEGER NOT NULL REFERENCES ingredients(ingredient_id)
);

-- レシピの材料
CREATE TABLE recipe_materials (
  recipe_id     INTEGER NOT NULL REFERENCES recipes(recipe_id),
  seq           INTEGER NOT NULL,      -- 元の並び順
  raw           TEXT NOT NULL,         -- 元の自由記述 "★醤油 大さじ2"
  ingredient_id INTEGER REFERENCES ingredients(ingredient_id),  -- NULL=正規化失敗
  PRIMARY KEY (recipe_id, seq)
);

CREATE INDEX idx_materials_ingredient ON recipe_materials(ingredient_id);
CREATE INDEX idx_materials_recipe     ON recipe_materials(recipe_id);
```

### 設計上のポイント

| # | 内容 |
|---|---|
| M-01 | `recipe_materials.raw` に**元テキストを必ず残す**。パーサを改良したとき、APIを叩き直さずDBだけ再生成できる |
| M-02 | `ingredient_id` が NULL = 正規化に失敗した材料。**捨てずにNULLで保持**し、パーサの改善対象として集計できるようにする |
| M-03 | 書き込みは行わない。お気に入り等のユーザーデータは**別DB**に置く（NFR-09：再ビルドで消さないため） |
| M-04 | `parent_id` は**2階層程度まで**に留める（`ねぎ` → `長ねぎ`）。深い階層は辞書整備の負担に見合わない |

## 5. 材料パーサ仕様（P-07）

`recipeMaterial` の自由記述から食材名を取り出す。**実装最大の山場。**

### 入力例と期待結果

| 入力 | 期待する食材名 |
|---|---|
| `玉ねぎ 1/2個` | 玉ねぎ |
| `★醤油 大さじ2` | 醤油 |
| `豚こま切れ肉 200g` | 豚こま切れ肉 |
| `塩コショウ 少々` | 塩コショウ |
| `○水 200cc` | 水 |
| `玉ねぎ（中）` | 玉ねぎ |
| `お好みで パセリ` | パセリ |

### 処理手順

```
1. 正規化    NFKC正規化（全角英数→半角）、前後の空白除去
2. 記号除去  先頭の装飾記号を除去: ★ ☆ ● ○ ◎ ■ □ ▲ △ ※ ・ ＊ * ◆ ◇ A) 1)
3. 括弧除去  （…）(…) 〈…〉 を除去
4. 分量除去  末尾の「数値＋単位」を除去
             単位: g kg mg ml cc L 個 本 枚 束 片 かけ 玉 パック 缶 袋
                   大さじ 小さじ カップ 合 cm 人分 適量 少々 適宜 お好みで ひとつまみ
             数値: 半角/全角数字、分数(1/2)、範囲(1〜2)、小数
5. 修飾語除去 先頭の「お好みで」「あれば」「なければ」「今回は」
6. 辞書照合  第6章へ
```

### 設計上のポイント

| # | 内容 |
|---|---|
| PR-01 | 分量が**先頭に来る**記述（`200g 豚こま`）も存在しうる。前後どちらも除去を試みる |
| PR-02 | 除去しすぎて空文字になった場合は、**除去前の文字列で辞書照合**にフォールバックする |
| PR-03 | パーサは純粋関数とし、**入力と期待結果の表をそのままユニットテストにする**。改良のたびに回帰を検出できるようにする |

## 6. 食材正規化仕様（FR-03）

### 辞書の構築

1. **文部科学省 日本食品標準成分表2020年版（八訂）** から食品名2,478件と別名を取り込み、`ingredients` の初期データとする（P-10）
2. 成分表の表記は `こまつな 葉 生` のような学術的表記なので、**口語の正規形へマッピングする変換規則**を別途用意する
3. 口語の表記ゆれ（`たまねぎ` `タマネギ` `玉葱`）を `ingredient_synonyms` に手動追加する
4. ETL 実行時に**正規化できなかった材料を頻度順で出力**し、上位から辞書へ追加する。この反復で辞書を育てる

### 照合順序

誤判定を防ぐため、**厳しい順に照合し、最初に当たった時点で確定**する。

```
① synonym 完全一致
② ingredients.name 完全一致
③ ひらがな/カタカナを揃えた上での完全一致
④ 最長部分一致（2文字以上。複数候補があれば最長を採用）
⑤ どれにも当たらなければ NULL（正規化失敗として記録）
```

> **④を無条件の部分一致にしてはならない。**
> 「油」が「醤油」に、「ねぎ」が「たまねぎ」に誤マッチする。
> 最長一致を優先し、候補の文字数が同じ場合は照合しない（NULLにする）。

### 音声テキストからの食材抽出（FR-02）

```
入力: "玉ねぎと豚こまと卵があります"

1. 文末表現の除去  「があります」「がある」「です」「かな」「だけ」
2. 分割           「と」「や」「、」「,」「あと」「それから」「以上」
3. 各断片を第6章の照合順序にかける  ← 材料パーサと同じ関数を使う（A-02）
4. 当たらなかった断片は「認識できなかった食材」としてユーザーに提示（FR-10）
```

## 7. 検索スコアリング仕様（FR-06 / FR-07）★本アプリの中核

### 食材のマッチング規則（D-03：階層の扱い）

2つの食材 a, b は、**同一、または一方が他方の祖先であるとき「一致」**とみなす。

| ユーザーの発話 | レシピの材料 | 判定 | 理由 |
|---|---|---|---|
| ねぎ（親） | 長ねぎ（子） | ✅ 一致 | 「ねぎがある」と言った人は、長ねぎを要求するレシピを作れる |
| 長ねぎ（子） | ねぎ（親） | ✅ 一致 | 「ねぎ」を要求する汎用レシピは、長ねぎで作れる |
| 長ねぎ（子） | 小ねぎ（兄弟） | ❌ 不一致 | 別物。兄弟間は一致させない |

**実装**：各食材の祖先チェーン（自分自身を含む）を求め、
`a のチェーンに b が含まれる` または `b のチェーンに a が含まれる` ならば一致。
階層は2段程度なので、ETL 時に各食材の祖先IDを非正規化して持たせてもよい（詳細設計で決める）。

> **兄弟間を一致させてはならない。**
> 「長ねぎ」と「小ねぎ」を同一視すると、料理として成立しない提案が出る。
> 親（ねぎ）を経由した一致だけを許す。

### 定義

所持食材集合 **P** = ユーザーが入力した食材 ∪ 常備品（`is_staple = 1`）
※ P との照合には上記のマッチング規則を用いる（単純なID一致ではない）

レシピ R について：

| 記号 | 意味 |
|---|---|
| **M** | R の材料のうち、`ingredient_id` が解決済み かつ `is_staple = 0`（＝**主要材料**） |
| **U** | R の材料のうち `ingredient_id` が NULL（＝正規化失敗・不明材料） |
| **matched** | \|M ∩ P\| |
| **missing** | \|M\| − matched |
| **coverage** | matched / \|M\|（\|M\| = 0 のときは対象外とする） |

### 並び順

```
第1キー: missing         昇順  ← 「あと何個買えばよいか」
第2キー: matched         降順  ← 手持ちを多く使えるレシピを優先
第3キー: coverage        降順
第4キー: |U|             昇順  ← 不明材料が少ない＝情報が確かなものを優先
```

### 表示グルーピング

| グループ | 条件 | 備考 |
|---|---|---|
| いま作れる | `missing = 0` | 常に展開表示 |
| あと1つで作れる | `missing = 1` | FR-11 を満たす |
| あと2つ | `missing = 2` | 折りたたみ |
| （非表示） | `missing >= 3` | 既定では出さない |

### なぜ「カバー率の閾値」ではなく「不足数」なのか（Q-02 への回答）

カバー率で足切りすると、**少ない材料で作れるレシピが落ちる**。

| レシピ | 主要材料 | 所持 | カバー率 | 不足 |
|---|---|---|---|---|
| X | 3個 | 2個 | **67%** | **1個** |
| Y | 10個 | 9個 | **90%** | **1個** |

閾値80%で切ると X が落ちるが、ユーザーにとっては**どちらも「あと1つ買えば作れる」で等価**。
むしろ材料が少ない X の方が作りやすい。
**ユーザーの意思決定は「あと何を買うか」で決まるため、不足数を第1キーに置く。**

### 不明材料（U）の扱い ★要決定（第10章 Q-06）

【推奨】**分母から外し、V3 で「確認が必要な材料」として明示する。**

- 不足扱いにすると、パーサ精度が低い初期段階で提案がほぼ消える
- 所持扱いにすると「作れると思ったら材料が無い」が起きる
- 分母から外した上で**正直に提示する**のが、誤誘導せず提案数も保てる

### 常備品リスト（UC-03 / FR-09）

`is_staple = 1` として所持扱いする。これが無いとほぼ全レシピが `missing > 0` になり提案が成立しない。

```
水 / 湯 / 塩 / こしょう / 砂糖 / 醤油 / 味噌 / 酢 / 酒 / みりん
サラダ油 / ごま油 / オリーブオイル / 片栗粉 / 小麦粉
だしの素 / 顆粒コンソメ / 鶏ガラスープの素 / マヨネーズ / ケチャップ
```

> **バター・にんにく・しょうが・卵・牛乳は含めない。**
> 家庭によって常備しているか分かれ、かつ**料理の成否を左右する**ため、
> 誤って所持扱いにすると提案の信頼性を損なう。

## 10. 決定事項

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **D-03** | 食材の粒度（Q-03） | **階層を持ち、親子間は一致・兄弟間は不一致とする** | 「ねぎがある」という自然な発話を拾いつつ、長ねぎと小ねぎの取り違えを防ぐ。`ingredients.parent_id` で表現（第7章） |
| **D-04** | 不明材料の扱い（Q-06） | **スコアの分母から外し、V3 で「確認が必要な材料」として明示する** | 不足扱いはパーサ精度が低い初期段階で提案が消える。所持扱いは誤誘導になる。除外した上で正直に提示するのが両立案 |
| **D-05** | 提案件数（Q-04） | **各グループ20件まで** | S3（離れて見る）を踏まえたスクロール量の現実解 |
| **D-06** | `assets/recipes.db` の git 管理（Q-07） | **管理しない。ETL で各自が再生成する** | サイズではなく**再配布の回避**が理由。公開リポジトリに楽天レシピのデータを置くことは、要件定義 P-08「個人利用に限定する」と矛盾する |
| **D-07** | ナビゲーション（Q-08） | **自前の状態管理（`useState`）で画面を切り替える** | 画面が3つのみ。依存を増やさない。必要になれば `expo-router` へ移行可能 |
