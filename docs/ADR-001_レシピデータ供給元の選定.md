# ADR-001：レシピデータ供給元の選定

| 項目 | 内容 |
|---|---|
| ステータス | **採用** |
| 決定日 | 2026-09-20 |
| 関連 | 要件定義 P-04〜P-09, FR-03, FR-06 |

---

## 背景

本アプリの中核要件は FR-06「所持食材をもとにレシピを検索する」である。
しかし調査の結果、**日本語レシピを食材名で横断検索できる公開 API は存在しない**ことが判明した。
そのため「どこからレシピデータを得るか」が、アーキテクチャ全体を決める最上位の設計判断となる。

---

## 選択肢の比較

| # | 選択肢 | 評価 |
|---|---|---|
| I | **日本食品標準成分表2020年版（八訂）／文部科学省** | **採用**。2,478食品・別名欄つき・Excel で無料公開・自由利用可 |
| J | 手書きで辞書を作る | 併用。I でカバーできない口語の表記ゆれを追加する |

---

## 決定

1. **レシピ本体は楽天レシピ API（選択肢 A）を採用する。**
   全カテゴリを巡回してローカル SQLite に蓄積し、食材検索は自前で実装する。
2. **食材正規化辞書のシードとして日本食品標準成分表（選択肢 I）を採用する。**
3. **海外 API（F/G/H）は採用しないが、退避先として記録に残す。**

---

## 根拠

- A は「食材検索ができない」という致命的に見える欠点を持つが、`recipeMaterial`（材料一覧）は取得できるため、
  **事前に巡回してローカル DB を構築すれば、検索機能は自前で作れる**。
  欠けているのは検索機能であってデータではない。
- C は本件にとって理想的なデータだが、利用条件を満たさない。**条件を満たさないデータは選択肢ではない**として明確に除外する。
- D は技術的には可能だが、利用規約違反である。
  「自分が毎日使うためのアプリ」に法的リスクを持ち込む合理性がないため、技術的可否に関わらず除外する。
- F/G/H は皮肉にも食材検索という本来機能を備えるが、
  「豚こま切れ肉」「長ねぎ」「白だし」といった日本の家庭の食材が扱えず、UC-01 が成立しない。
- I により、ゼロから手書きする想定だった正規化辞書の大部分が自動生成できる。
  ただし成分表の表記は `こまつな 葉 生` のような学術的表記であり、
  **口語の表記ゆれ（たまねぎ／玉ねぎ／タマネギ／玉葱）は J で別途補う必要がある。**

---

## 結果として受け入れる制約

| # | 制約 |
|---|---|
| C-01 | レシピ件数は「全カテゴリ数 × 4件」が上限。**実測値：カテゴリ2,161件（大43／中544／小1,574）× 4 = 最大8,644件（重複含む）**。網羅性は期待できない |
| C-02 | 調理手順は DB に持てない。`recipeUrl` を WebView で開く（D-01） |
| C-03 | `recipeMaterial` は自由記述のため、分量・記号を除去するパーサが必須（P-07） |
| C-04 | レシピの鮮度はローカル DB を再生成したタイミングに依存する |
| C-05 | 取得データの蓄積は個人利用に限定する。App Store 公開は別途規約確認が必要（P-08） |

---

## 将来の見直し条件

以下のいずれかが起きた場合、本 ADR を再検討する。

- C-01 のレシピ件数不足が実使用で問題になった場合 → 選択肢 F（Spoonacular）の併用を検討
- 楽天レシピ API が提供終了・仕様変更した場合
- App Store 公開を目標に含める判断をした場合（Q-05）→ C-05 の規約確認が必須になる

## 楽天ウェブサービス アプリ登録の申告内容（2026-09-20 時点）

API 利用条件と実装を一致させるため、登録時の申告内容を記録する。
**実装がこの申告から逸脱しないこと**（特に QPS）。

| 項目 | 申告値 | 備考 |
|---|---|---|
| Application type | **API/Backend Service** | 選択肢は `Web Application` / `API/Backend Service` の2つのみ。API を叩くのは開発PC上の ETL スクリプトでありブラウザではないため後者を選択 |
| Expected QPS | **1** | ETL は 1 秒 1 リクエストに制限する。**この値は実装上の制約であり、守ること** |
| API Access Scopes | Rakuten Recipe API のみ | 使用しないスコープは取得しない |
| Allowed IP addresses | 開発機のグローバル IPv4 ＋ IPv6 の **/64 プレフィックス** | `Application type` に `API/Backend Service` を選ぶと、欄が `Allowed websites`（ドメイン）から `Allowed IP addresses`（送信元IP）に変わる。値は楽天の管理コンソール側が正。**本リポジトリは公開のため、実際の IP はここに記載しない** |
| Purpose of data usage | 個人利用・非商用、手順は保持せず `recipeUrl` へ送客する旨を明記 | |

### C-06（解決済み）

当初 `Allowed websites`（ドメイン）の判定挙動が不明だったが、
`Application type = API/Backend Service` を選択すると **`Allowed IP addresses`（送信元IP）に変わる**ことが判明。
Node スクリプトからの利用でも判定は明確であり、懸念は解消した。

### C-06 補足：疎通検証の結果（2026-09-20 実施）

Node から実際にリクエストし、以下を確認した。

- 認証（`applicationId` + `accessKey`）：**成功（HTTP 200）**
- **IPv6 `/64` プレフィックス登録は有効**。Node は IPv6 の temporary アドレスで接続しており、それが許可された（C-07 の対策が機能することを実証）
- カテゴリ総数：**2,161件**（大43／中544／小1,574）
- ETL 所要時間：1 QPS 厳守で**約36分**

### C-08（重要）：2026年のAPI仕様変更 — 旧エンドポイントは廃止済み

楽天ウェブサービスは 2026年2月〜5月に移行を実施し、**2026年5月14日に旧ドメインを完全停止**している。

| | URL |
|---|---|
| 旧（**使用不可**） | `https://app.rakuten.co.jp/services/api/Recipe/...` |
| **新（使用する）** | `https://openapi.rakuten.co.jp/recipems/api/Recipe/CategoryList/20170426` |

あわせて認証方式も変更された。

- `applicationId` は**数字20桁から UUID 形式へ**
- `accessKey` が**新たに必須**
- 両方を**クエリパラメータ**で送る（`Authorization` / `x-api-key` ヘッダーは無視される。検証済み）

**ネット上の解説記事・サンプルコードの大半は旧仕様のまま**なので、参照する際は必ずエンドポイントのドメインを確認すること。
旧エンドポイントに新形式の UUID を送ると `400 {"error":"wrong_parameter","error_description":"specify valid applicationId"}` が返り、
一見「IDが間違っている」ように見えるが、実際はエンドポイントが原因である。

### C-07（追加制約）：送信元 IP の変動

開発機は macOS のプライバシー機能により、**外向き通信に IPv6 の `temporary` アドレスを使用する**（`ifconfig` で確認済み）。
このアドレスは定期的にローテーションするため、個別アドレスを登録すると短期間で疎通不能になる。

**対策**：IPv6 は個別アドレスではなく **/64 プレフィックスで登録する**。
一時アドレスが変わっても前半64ビットは不変のため吸収できる。

**運用上の注意**：
- ルーター再起動・長時間の回線断により、ISP 配布の /64 プレフィックス自体が変わることがある
- VPN 接続中、テザリング、外出先 Wi-Fi では送信元 IP が変わり拒否される
- **ETL が全件失敗した場合、コードより先に送信元 IP を疑うこと**

**補足**：Node は IPv4 が利用可能でも IPv6 を優先する場合がある。
疎通確認は実際に Node から行い、`curl` の結果だけで判断しないこと。
